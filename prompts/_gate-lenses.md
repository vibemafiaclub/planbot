1. **구조화 부족** (id: `structuring`) — 화면 설명/처리 조건/데이터 항목이 항목별로 구분돼 있는가, 아니면 문단 하나에 뒤섞여 있는가.
2. **과도한 용량** (id: `excessive_volume`) — 담고 있는 실제 정보량에 비해 파일 용량이나 분량이 과도한가 (예: 고해상도 스크린샷 수십 장, 불필요하게 긴 전체 회의록 통째 첨부).
3. **텍스트를 이미지로 전달** (id: `text_as_image`) — 원고 내용이 텍스트로 쓸 수 있는데도 스크린샷/사진으로만 전달돼 OCR 유실 위험이 있는가. (다이어그램·실제 화면 목업처럼 이미지가 본질적으로 필요한 경우는 해당 없음)
4. **자체 어휘 사용** (id: `vocabulary_mismatch`) — 원고 속 도메인 개념어를 레포에서 grep해봤을 때, 코드/문서 어디에도 대응하는 이름이 없이 작성자만의 용어로 쓰이고 있는가. 별도 용어집을 만들지 말고, 원고에서 개념어를 뽑아 그때그때 검색해 판단한다.
5. **UI 위치 특정 실패** (id: `ui_location_precision`) — 작업할 화면/컴포넌트 위치를 화면명·메뉴 경로·컴포넌트명 같은 어휘로 짚었는가, 아니면 스크린샷에 빨간 박스/화살표 같은 시각적 마킹에만 의존하는가.
6. **AS-IS/TO-BE 미명시** (id: `as_is_to_be_missing`) — 기존 동작을 바꿔달라는 수정 요청인데, 현재 어떻게 동작하고(AS-IS) 어떻게 바뀌어야 하는지(TO-BE)가 구분돼 있지 않은가. (신규 기능 요청에는 해당 없음)
7. **검색 가능한 앵커 부재** (id: `no_searchable_anchor`) — 화면명·API 엔드포인트·테이블명·지라 티켓번호처럼 레포에서 실제로 검색해 찾아갈 수 있는 구체적 식별자가 하나도 없거나, 있어도 그것만으로는 작업 대상을 특정할 수 없는가 (예: 선행 티켓 번호 하나뿐이라 결국 전체를 다시 뒤져야 하는 경우).
